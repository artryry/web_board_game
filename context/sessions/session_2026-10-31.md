# Session 2026-10-31: M1 (Auth)

## Summary
We planned and implemented milestone **M1**. Users can register, log in, refresh their tokens and read their own profile (`/api/auth/me`). Any route can require a logged-in user by taking a `CurrentUser` parameter. All errors now share one body shape, `{"detail": {"code", "message"}}`. API tests run against a real Postgres test database. Every check passes, and the endpoints were tested by hand through nginx. Nothing is committed yet.

## Starting point
- M0 was done and committed (`9d0747a`) on the `m1-auth` branch.
- There was no `users` table, no error format, no JWT or password-hashing library, and no test database. The only tests were for `/api/health`, using fakes.
- [current-feature.md](../current-feature.md) already held the M1 task list and "done when" criteria.

## How it went
1. **Plan.** In plan mode we read the M0 code and the plans, wrote the M1 plan, and asked two questions:
   - Test DB lifecycle: **create only if missing** (the user's choice; recreating it on every run was the other option).
   - Should FastAPI's own errors (404, 405) use our error shape? **Yes.**
2. **Implementation**, following the plan step by step. A short-circuit bug in `authenticate` (`user is None or ...` skipped the dummy password verify) was caught and fixed during the work.
3. **Afterwards the user removed the dummy-hash timing defence** (see decisions). The code, tests and docs were checked again against that version.

## Decisions made

| Topic | Decision |
|---|---|
| Login | Email and password. Usernames are public, emails stay private. |
| IDs | UUID primary keys (`uuid4`), so ids can't be guessed or counted. This is the pattern for every later table. |
| Tokens | Stateless HS256 JWTs with claims `sub`, `type` (`access`/`refresh`), `iat` and `exp`. Access tokens last 15 min and refresh tokens 30 days. `refresh` issues a new pair. There is no revocation in M1. |
| JWT settings | `JWT_SECRET` needs at least 32 characters (256 bits). `JWT_ALGORITHM` is limited to HS256/HS384/HS512, because the secret is symmetric. |
| Error body | `{"detail": {"code", "message"}}` for our `AppError` and for FastAPI's HTTP errors (code = snake_cased status phrase, e.g. `not_found`). 422 keeps FastAPI's default body until M4. |
| 401 responses | Always carry `WWW-Authenticate: Bearer` (RFC 9110). The codes are specific: `invalid_credentials`, `not_authenticated`, `token_expired` (the client should refresh), `token_invalid` and `token_wrong_type`. |
| 409 responses | `username_taken` / `email_taken`. If two registrations race, the DB unique violation is caught and turned into the same 409. |
| Register status | 201. Login and refresh return 200. |
| Uniqueness | Case-insensitive unique indexes on `lower(username)` and `lower(email)`. Usernames keep their case for display. Emails are stored lowercased. |
| Password hashing | argon2id via `pwdlib`, run in a thread (`asyncio.to_thread`) so the ~50 ms of CPU doesn't block the single-worker event loop. |
| Login timing | **No dummy-hash defence** (removed by the user). An unknown email fails without running argon2. Register already reveals whether an email exists, so hiding it on login added nothing. |
| Constraint names | `Base.metadata` has a naming convention (`pk_`, `uq_`, `ix_`, `fk_`, `ck_`), so later migrations can drop or alter constraints by name. |
| Test DB | `<POSTGRES_DB>_test` in the same container, created if missing and migrated with `alembic upgrade head` on every run. Each test runs in a transaction that is rolled back (`join_transaction_mode="create_savepoint"`, so service commits only touch savepoints). |
| Dependencies | `pwdlib[argon2]==0.3.1`, `PyJWT==2.15.1`, and `email-validator==2.3.0` (needed by Pydantic's `EmailStr`). |

## Verification
- `pytest` (40 passed, re-run after the dummy-hash removal), `ruff check`, `ruff format --check` and `mypy app tests` are all clean.
- On the dev DB, `alembic upgrade head` → `downgrade -1` → `upgrade head` run cleanly. `alembic check` finds no drift between the models and the DB. `\d users` shows `pk_users` and both `lower()` unique indexes.
- By hand, through nginx (`http://localhost/api`):
  - register gives 201; a duplicate username gives 409 `username_taken`
  - login gives 200; a wrong password gives 401 `invalid_credentials` with `WWW-Authenticate: Bearer`
  - `/me` gives 200 with a token; without one, 401 `not_authenticated`
  - refresh gives 200; an access token instead gives 401 `token_wrong_type`
  - an unknown route gives 404 in the shared error shape
  - `/api/health` still returns 200
  - the OpenAPI schema has the `HTTPBearer` scheme, so `/docs` shows an Authorize button
- The user created for the manual check was deleted from the dev DB.

## Notes
- `test_auth.py` and `test_migrations.py` need Postgres (`docker compose up -d`). The other test files don't.
- If a migration is edited in place without a new revision id, drop `cardtable_test` by hand so it gets rebuilt.
- Each refresh issues a new 30-day refresh token, so a session never expires while it's used, and old refresh tokens stay valid until their own `exp`.
