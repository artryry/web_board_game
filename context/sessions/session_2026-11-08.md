# Session 2026-11-08: refresh token in an HttpOnly cookie

## Summary
At the user's request, the refresh token moved from `localStorage` into an HttpOnly cookie, so no script (and no XSS) can read it. This is on the `f0-auth` branch, on top of the uncommitted F0 work. Nothing is committed yet.
- Results: 368 backend tests and 38 Vitest tests pass, the e2e test passes through nginx, and lint, format, types and build are clean.
- Earlier in the session: the app must be opened at `http://localhost/` (nginx), not at Vite's `:5173`, which has no `/api` proxy.

## Decisions made

| Topic | Decision |
|---|---|
| Cookie | `refresh_token`, with `HttpOnly`, `SameSite=Strict`, `Path=/api/auth` and `Max-Age` = the refresh TTL. `Secure` comes from the new setting `REFRESH_COOKIE_SECURE` (default true; browsers accept Secure cookies on `http://localhost`). |
| Bodies | Register, login and refresh return only `{access}`. `/refresh` reads only the cookie; without it, the answer is 401 `not_authenticated`. |
| Logout | New `POST /api/auth/logout` (204, needs no access token) deletes the cookie, because scripts can't. It revokes nothing: tokens stay stateless. |
| CSRF | `SameSite=Strict` keeps other sites from using the cookie, so no CSRF token is needed. The app and `/api` must share one origin (nginx does this). |
| Session hint | `localStorage['cardtable.session']` (not secret) says a session exists. Without it, the app starts logged out without a request. Removing it still logs out the other tabs through the `storage` event. |
| Late refresh | A refresh answer that arrives after a logout has set a new cookie, so the client calls `/logout` again. Otherwise the cookie would outlive the logout, or after a quick switch to another account, a later refresh could log the tab into the old account. |

## Notes
- A browser that was logged in before this change still has the old `cardtable.refresh` entry in `localStorage`. Nothing reads it any more; clearing the site data removes it.
- The access token still lives in memory, so an XSS could use the session while the page is open. The cookie only stops it from taking the long-lived token away.
