# Coding standards

Rules for keeping the code clean, scalable and consistently structured. The directory layouts in [backend_plan.md §3](backend_plan.md) and [frontend_plan.md §2](frontend_plan.md) are the reference structure. New code goes where those layouts say.

## 1. General

- **Readable over clever.** Clear names, short functions, early returns, no deep nesting.
- **One responsibility per module, class and function.** If you need "and" to describe it, split it.
- **No duplication of logic.** Shared rules live in one place (for example the cost formula lives in `engine/cost.py` and is mirrored once on the frontend, with the same test cases).
- **No dead code.** No commented-out code, unused imports or TODOs without context. A TODO must say what and why.
- **Naming:**
  - Use domain names from the plans: `origin`, `field_effect`, `section`, `lane`, `ruleset`, `phase`, `legal_actions`.
  - Use the same name for a concept everywhere: the database, the API, the engine and the UI.
- **Comments explain *why*, not *what*.** The code shows what it does.
- **Configuration comes from settings or env vars**, never hard-coded: URLs, secrets, limits, timeouts.
- **Fail loudly.** Validate input at the boundaries (API, WebSocket, rules JSON), and raise specific errors. Never swallow exceptions silently.
- **Pin dependency versions** (`requirements.txt`, `package-lock.json`).

## 2. Backend (Python / FastAPI)

### Style
- Python 3.12, with type hints on every function signature. The code must pass `mypy` (strict on `app/engine`).
- Format and lint with `ruff` (format and check), with a line length of 100.
- `snake_case` for functions and variables, `PascalCase` for classes, `UPPER_CASE` for constants.
- `async` all the way for I/O: DB, Redis and R2 (storage). Never call blocking I/O inside an `async def`.

### Layers (dependencies point down only)
```
api/ , ws/          HTTP / WebSocket handling: parse input, call a service, return a schema
services/           use-case logic, transactions, Redis/R2 orchestration
engine/             pure game logic: NO imports of fastapi, sqlalchemy, redis or storage
models/             SQLAlchemy ORM (DB shape only)
schemas/            Pydantic DTOs (API shape only)
core/               config, security, db session, dependencies
```
- **Routers stay thin.** They have no business logic and no raw queries: they validate, call a service and return a response model.
- **Never return ORM objects from the API.** Always return Pydantic `schemas` with `response_model`.
- **The engine is pure and deterministic.** All randomness goes through `engine/rng.py` with the game seed. Nothing in the engine reads the clock or touches I/O.
- **Modules extend the game.** New phases, features, spells and field effects are new classes registered with a decorator in `engine/modules/<kind>/`. Each has a `Params` model and tests. The engine core must not branch on specific module keys.

### API
- Routes live under `/api/<resource>`, with plural nouns and REST verbs.
- Errors use the right status codes (400, 401, 403, 404, 409, 422) and the body `{"detail": {"code": "<machine_code>", "message": "<human text>"}}`.
- Check ownership in the service layer. A user can only change their own resources.
- List endpoints are paginated (`limit` and `offset`).

### Database
- Every schema change goes through an **Alembic migration**. Never edit the DB by hand.
- Table names are plural `snake_case`. Every table has `id`, plus `created_at` and `updated_at` where it makes sense.
- JSONB columns (`abilities`, `field_effects`, `definition`) are always validated by a Pydantic model before they are written.

## 3. Frontend (React / TypeScript)

### Style
- TypeScript `strict`, with no `any` (use `unknown` and narrow it). ESLint and Prettier.
- Function components and hooks only. `PascalCase.tsx` for components, `camelCase.ts` for hooks and utilities, and hook names start with `use`.
- One component per file. Split a component when it grows past about 200 lines.

### Structure and state
- Organise code by **feature** (`features/cards`, `features/game`, …). Shared UI lives in `ui/` and has no domain logic.
- **Server data** goes in TanStack Query hooks in `api/hooks/`. Components never call `fetch` directly.
- **Live room and game state** goes in the Zustand `gameStore` only. Don't copy server data into local state.
- API types come from the generated `schema.d.ts`. Don't write API types by hand.
- **Never re-implement game rules.** Whether a card can be dragged and where it can be dropped comes only from `legal_actions`.
- Module settings forms are generated by `SchemaForm` from the catalog. Don't write a form for one specific module.

### UI
- Style with Tailwind utility classes. Use shared design tokens (colours, spacing) from the Tailwind config, not one-off values.
- Accessibility: use semantic elements, give interactive controls labels, make everything work with the keyboard, and offer click-to-target as well as drag.

## 4. Testing

- New logic comes with tests in the same change.
- **Engine:** unit tests for every module, golden replay tests and board-size tests (see [backend_plan.md §12](backend_plan.md)).
- **Backend API:** pytest with httpx against a test database. One test file per router.
- **Frontend:** Vitest and React Testing Library for logic and components, and Playwright for end-to-end flows.
- Tests are deterministic: no real network calls, no sleeps, and fixed seeds.

## 5. Git

- Use small commits with one logical change each. Messages are in the imperative mood (`Add origin CRUD endpoints`).
- Work on feature branches named after the milestone or feature (`m0-infra`, `f1-card-editor`), and merge into `main`.
- Never commit `.env`, secrets, `venv/`, `node_modules/` or build output.
